# Incident 2026-11-27 — épuisement NPROC par l'application

## Résumé

L'application a consommé 134 threads (deux instances lsnode de 67 threads) sur un quota NPROC de 165 partagé avec WordPress/PHP. CloudLinux a enregistré 8 676 dépassements de NPROC en 24 h ; WP Toolkit échouait avec `cagefs_enter_user: Unable to fork`.

## Faits vérifiés (production)

- Deux processus lsnode de l'application, **PPID=1**, 67 threads chacun, RSS ≈ 242 Mo et 285 Mo.
- 56 CPU logiques visibles (affinité 0-55) ; 56 threads `tokio-runtime-w` par instance.
- RESTART et STOP APP de cPanel n'ont libéré aucun des deux processus.
- SIGTERM envoyé directement aux deux PID vérifiés : arrêt réussi.
- `TOKIO_WORKER_THREADS=2` ajouté à l'environnement cPanel ; après START APP : PID 1355617, PPID 1182422, **13 threads dont 2 Tokio**, RSS 241 428 Kio, affinité toujours 0-55.
- **Même PID 1355617 après 1 h 21 (ELAPSED 01:21:23) : PPID = 1**, 13 threads (NLWP), RSS 256 212 Kio (+6 %). Une seule instance Node.
- Environnement : GNU libc 2.34, x86_64, Node 22.23.5 (`/opt/alt/alt-nodejs22/root/usr/bin/node`, hors du PATH du shell par défaut).
- `server.js` en production : serveur HTTP Next.js minimal, sans gestionnaire SIGTERM, sans `npm`, `sh`, `cluster` ni sous-processus.

## Cause racine du nombre de threads (établie)

Le runtime natif SWC de Next.js crée autant de threads Tokio que de CPU visibles ; CageFS/LVE limitent le temps CPU mais pas le nombre de CPU visibles. 11 threads fixes (libuv 4, V8 4, principal et auxiliaires 3) + 56 = 67.
Reproduction locale (`ops/probe.sh`) : Tokio suit le nombre de CPU visibles (1 → 1, 4 → 4) ; `TOKIO_WORKER_THREADS=2` donne 13 threads, comme en production.

## Cause de l'échec de RESTART/STOP : non établie

Ce que l'on sait : Node s'arrête sur SIGTERM puisque `server.js` n'a pas de gestionnaire (confirmé par l'arrêt manuel). **Le PPID=1 des deux anciennes instances ne prouve rien** : le PID 1355617, sain et lancé par cPanel, est lui-même passé du PPID 1182422 au PPID 1 en cours de vie. LiteSpeed change donc la relation de parenté de ses processus Node dans le fonctionnement normal ; la cause de ce changement n'est pas établie.

Correction d'une formulation antérieure de ce document : les anciennes instances n'étaient pas « orphelines » au sens d'une anomalie établie, et rien ne permet d'expliquer l'échec de RESTART/STOP par leur PPID.

Hypothèses **écartées** par le `server.js` réel : démarrage via `npm`/`sh` qui intercepterait le signal ; gestionnaire SIGTERM qui bloquerait l'arrêt ; sous-processus ou cluster créés par l'application.

Hypothèses **restantes, non vérifiées** : cPanel/lsnode suit ses instances par un mécanisme que l'on ignore (fichier de PID, titre de processus, groupe de contrôle) et a cessé de reconnaître les deux anciennes ; un redémarrage du gestionnaire lsnode a laissé des instances sans les rattacher à l'application ; autre mécanisme propre à l'hébergement. Aucune n'est conclue.

À relever si le cas se reproduit (avant tout arrêt manuel), pour la demande à VinaHost :

```bash
ps -eo pid,ppid,lstart,etimes,nlwp,rss,args --forest | grep -E 'lsnode|node'
```

Heure de création de chaque instance par rapport à l'heure des RESTART/STOP, journaux lsnode/cPanel de la période, résultat de `ops/verify.sh --deployed-at …`. Le PPID est à relever mais ne doit déclencher aucun arrêt.

## Actions réalisées

1. Arrêt de deux PID vérifiés par SIGTERM (aucun `kill -9`, aucun `pkill`).
2. `TOKIO_WORKER_THREADS=2` dans cPanel : 134 → 13 threads.

## Actions de prévention (cette branche)

- `ops/server.js` : garde `TOKIO_WORKER_THREADS=2` avant tout `require()`, serveur HTTP inchangé.
- `ops/probe.sh` + `.github/workflows/runtime-resources.yml` : non-régression des threads, Tokio, mémoire, connexions PostgreSQL.
- `ops/preflight.sh`, `ops/verify.sh`, `docs/ops/runbook.md` : le succès d'un redémarrage est vérifié, jamais présumé.
- Secrets par défaut publics refusés en production (groupe de commits distinct).
